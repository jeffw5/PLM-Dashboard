Purpose

A categorized set of Claude skills, each to one template, each with source lineage

Every skill in the Evaluate stage of the ingestion pipelines is a Claude Skill built to one consistent template and traceable to the authoritative body of knowledge it enforces. This document defines that template, shows one skill fully worked against it, and catalogs the starting-point set across eleven disciplines — so a team can build them without re-deciding structure or provenance each time.

1

The consistent skill template

Every skill is a folder with a SKILL.md (the same fields in the same order) plus bundled rubric and reference cards. The frontmatter carries identity and lineage; the body carries the evaluation contract. This is what makes 90 skills interoperable and auditable.

Template fields

FieldPurpose
nameStable skill id.
descriptionPushy trigger — when Claude should invoke this skill (artifact types, keywords).
versionSemver; rubric changes bump the version for auditability.
categoryOne of the eleven disciplines.
source_lineageAuthoritative source(s) with edition and section/clause and URI — the provenance of every criterion.
maps_toPLM discipline, the Evaluate agent that runs it, and the PLM artifact slots it scores.
scopeThe inputs / artifact types this skill evaluates.
rubricAnchored 0–3 dimensions with explicit anchor text (low variance).
defect_modelWhat is a major (gate-tripping) vs minor (advisory) non-conformance for this skill.
risk_modelHow this skill's defects map to likelihood × impact.
output_contractUniform JSON returned to the PLM ingestion model.
governanceConfidence threshold below which the circuit-breaker routes to human review (MTBH).
referencesFull citations — the section-level lineage behind each rubric line.

SKILL.md scaffold

Copy this to start any skill.

name: se-requirements-quality
description: Run when evaluating a stakeholder or system requirements artifact for quality and traceability. Triggers on requirement specs, req lists, SRS, needs statements.
version: 1.0.0
category: Systems Engineering
source_lineage:
  - title: INCOSE Guide to Writing Requirements (GtWR)
    edition: v4, 2022
    reference: characteristics of individual requirements
    uri: ref://incose/gtwr
  - title: ISO/IEC/IEEE 15288
    edition: 2023
    reference: §6.4.3 System Requirements Definition
    uri: ref://iso/15288
maps_to:
  discipline: Requirements
  evaluate_agent: Discipline Skill Agents (Pipeline B)
  plm_slots: [define.*, discover.persona*]
---

# System Requirements Quality

## Scope
Which artifacts/inputs this skill evaluates and what it ignores.

## Evaluation criteria (rubric)
Anchored 0-3 dimensions. Each dimension: name, what 0/1/2/3 look like,
and the evidence locator the score must cite.

## Defect model
- major: source-mandated element missing or wrong (gate-tripping)
- minor: quality/style shortfall (advisory; accrues as debt)

## Risk model
likelihood x impact per defect; impact weighted by criticality and phase.

## Output contract (returned to PLM model)
{ conformance: 0-3, defects: [{severity, ref, evidence}],
  risk: {L, I, E}, confidence: 0-1, lineage: [...] }

## Governance
If confidence < 0.6 -> circuit-breaker routes to human review (MTBH).

## References
Full citations with section-level lineage for every rubric line.
The output_contract is identical for every skill, which is why heterogeneous evaluations converge cleanly into the PLM ingestion model and the console's scoring. The source_lineage block is mandatory — a skill with no traceable source is not accepted into the library.

Worked example

One skill instantiated fully against the template, so every other skill has a concrete pattern to copy.

stpa-unsafe-control-actions STPA

Source lineage: STPA Handbook (Leveson & Thomas, 2018), Step 3 — Identify Unsafe Control Actions · Engineering a Safer World (Leveson, 2011). ref://stpa/handbook#step3

Scope

Evaluates hazard-analysis artifacts that model a control structure and enumerate control actions — safety cases, STPA worksheets, control-structure diagrams. Requires a defined loss/hazard set (from the losses-and-hazards skill) and a control structure (from the control-structure skill).

Evaluation criteria (rubric)

0 Absent — no UCAs identified for the control actions.
1 Deficient — UCAs for some actions; the four UCA types not systematically applied.
2 Adequate — all control actions assessed against the four UCA types; traced to hazards.
3 Strong — complete UCA set, each traced to hazard and forward to a safety constraint, with context.

The four UCA types: providing causes hazard · not providing causes hazard · wrong timing/order · wrong duration (stopped too soon / applied too long).

Defect model

  • Major — a control action with no UCA analysis, or a hazard with no covering UCA (safety gap). Gate-tripping.
  • Minor — UCA present but missing context or not linked forward to a safety constraint. Advisory.

Risk model

Each unmitigated UCA: likelihood from control-loop exposure, impact from the severity of the linked loss. A major on a safety-critical loss is Critical exposure and a hard gate in the console.

Output contract

{ conformance: 2, defects: [{severity:"major", ref:"UCA-brake-not-provided", evidence:"CSD §3.2"}],
  risk: {L:4, I:5, E:20}, confidence: 0.74, lineage: ["STPA Handbook §Step3","doc://safety-case-v2"] }

Governance

Confidence below 0.6 (e.g., control structure incomplete) routes to a safety reviewer rather than scoring. STPA-Sec variant extends the same template to security losses.
